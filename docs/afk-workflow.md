# 单轮 AFK 工作流

每轮只处理一张可执行 Issue。需求、规格或原型已有结论时直接复用，避免重新从头讨论。

- [ ] `/grill-with-docs`：需求不清楚时澄清业务，更新术语和 ADR。
- [ ] `/prototype`：用最小原型回答文字讨论无法验证的问题，记录实测边界。
- [ ] `/to-spec`：将已确认方案固化为规格。
- [ ] `/to-tickets`：拆成可评审、可独立验收的工单，登记真实依赖。
- [ ] Sandcastle：先检查环境与 Git 基线，再在隔离环境中执行一张工单。
- [ ] `/code-review`：固定本轮基点，独立检查 Standards 与 Spec，修复实质问题。
- [ ] 主机验收：真实模型、PDF、存储和浏览器验证通过后，再按已获授权提交与 push。
- [ ] `/improve-codebase-architecture`：在有具体维护问题时单独评估，避免为简单任务扩大重构。
- [ ] `/handoff`：确实需要新会话时，传递分支、commit、运行进程、报告、遗留问题和下一步。

## 本项目的检查点

1. 读取 `.sandcastle/results/` 跳过已完成任务；用 GitHub 原生依赖检查 blocker。保持 OPEN 的 blocker 不因本地已有实现而自动解除。
2. 沙箱使用 Linux 临时 venv；主机已有模型和浏览器由主协作者复用，不重复下载大模型或 Chromium。
3. 单元测试与真实验收分开记录。使用随机测试库、collection 和 bucket，检查清理结果；不得将 mock 通过当作真实模型通过。
4. 新功能需验证旧数据 schema、故障恢复、用户隔离、Windows 行为和真实框架返回类型。随机 ID 的回归使用固定反例，避免概率性漏检。
5. 脱敏只改变业务内容，不改变主键或归属标识；Markdown 标签与表格也需覆盖。
6. 提交前检查 diff、敏感信息、测试证据；push 后核对远端 SHA。合并、关闭 Issue 和部署按用户后续指令执行。

## 本轮遗留维护建议

#4 审查发现多个导入节点以 `owner_id` 判断异常日志及备份行为。当前测试已覆盖个人策略的隐私行为；后续若出现第三种文档模式，再集中定义导入隐私策略，避免本轮增加没有业务需求的抽象。
